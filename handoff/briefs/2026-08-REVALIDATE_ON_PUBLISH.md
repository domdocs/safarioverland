# Brief — Revalidate on publish

**Date:** 2026-08-07
**For:** Claude Code (local, Crucial SSD working copy)
**Branch:** `fix/revalidate-on-publish` off `main`
**Size:** small — roughly ten lines plus a test

---

## Why

Publishing a field note leaves it invisible for up to an hour.

`app/sitemap.ts` and `app/field-notes/page.tsx` both carry `export const revalidate = 3600`. When an article's status flips to `published`, nothing tells Next.js those cached pages are stale, so the piece is live at its own URL but absent from the index and the sitemap until the window elapses.

This was felt twice on 7 August: once when the first field note published and Dom reported "I don't see it" — the article was rendering correctly at its own URL the whole time — and once during verification. It reads as broken even though nothing is.

It matters more once routines publish unattended. A scheduled run that publishes at 06:00 and reports success, against a site that will not show the piece until 07:00, makes the Sunday digest's preview links unreliable and the trust ladder harder to audit.

---

## What to do

Call Next's `revalidatePath` when an article's published state changes.

In `app/api/admin/articles/[id]/route.ts` (PUT) and `app/api/admin/articles/route.ts` (POST):

```ts
import { revalidatePath } from "next/cache"

// after a successful write that results in status === "published",
// or that transitions a previously published article away from it
revalidatePath("/field-notes")
revalidatePath("/sitemap.xml")
revalidatePath(`/field-notes/${article.slug}`)
```

Three cases must all invalidate, not just the happy one:

1. **draft → published** — the new article must appear
2. **published → draft or archived** — an unpublished article must *disappear* from the index and sitemap, which matters more; leaving a retracted piece listed for an hour is worse than a delay in adding one
3. **a published article's slug changes** — revalidate both the old and new paths

Also revalidate on `DELETE` of a published article, for the same reason as case 2.

Do not add `revalidatePath` unconditionally on every write. A draft being edited repeatedly should not be busting the sitemap cache each time.

**Leave `revalidate = 3600` in place.** It is the backstop for anything that changes outside the API — a direct database edit, a listing approved through the listings admin. This brief adds precision, it does not replace the window.

---

## Watch for

`revalidatePath` must be called from a request context. Both routes already export `dynamic = "force-dynamic"` and run on the Node runtime, so this should be straightforward — but if it throws or silently no-ops, say so rather than working around it.

Confirm `/sitemap.xml` is a revalidatable path in this app's routing. It is generated by `app/sitemap.ts` as a route handler, so `revalidatePath("/sitemap.xml")` should be correct; if Next expects a different key for metadata routes, find out rather than guessing, and note what you found.

---

## Acceptance criteria

1. Publishing an article makes it appear in `/field-notes` and `/sitemap.xml` on the **next request**, with no hour's wait and no redeploy
2. Un-publishing (to `draft` or `archived`) removes it from both on the next request
3. Deleting a published article removes it from both on the next request
4. Editing a draft does not invalidate the sitemap
5. `revalidate = 3600` still present on both routes
6. A test covers cases 1 and 2
7. `pnpm build` clean on Node 20.19.6 / pnpm 10; `pnpm test` green

**Verify on production after deploying, not on the preview.** A preview serves its build-time prerender and will look correct either way — that is exactly how the sitemap regression in PR #18 got through.
